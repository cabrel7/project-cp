# Spec P2.3 : connexion Google (inscription, connexion, liaison, déliaison), boutons clé d'accès et Apple masqués

## 0. Résumé

1. **Périmètre (D67)** : seulement Google.
   - Connexion et inscription par Google.
   - Liaison :
     - en attente, quand l'e-mail correspond déjà à un compte : écran G8 ;
     - depuis une session : API et page minimale.
   - Déliaison.
   - `GET /methods`.
   - Les boutons « clé d'accès » et « Apple » sont **masqués**. Leur affichage dépend d'un indicateur servi par `GET /methods`, qui vaut `false` en P2.3.
   - Tout le reste de l'ancienne spec part en **P8.8** : sous-lots a et b, Apple, R2, Q1, Q3, Q4, D-c. Voir §8 et l'annexe P8.8, qui conserve CA, contrats et migrations.
   - P2.2c (plafond SMS) reste hors lot, dans une autre session.
2. **Rattachement jamais automatique** (D67). Une identité Google inconnue dont l'e-mail correspond à un compte existant ne crée rien et ne connecte personne. Elle crée une **liaison en attente** de 10 min (Redis + cookie `cp_link`). Cette liaison n'est rattachée qu'après **une connexion au compte existant faite après l'étape Google** (mot de passe ou téléphone), puis une confirmation explicite.
   - Un compte `pending` (e-mail non vérifié) ne peut ajouter aucun moyen de connexion : `AUTH_ACCOUNT_NOT_VERIFIED`.
   - Les jetons Google (accès, rafraîchissement, `id_token`) ne sont **jamais** conservés : ni en base, ni dans Redis, ni dans les journaux.
3. **Sans ré-authentification** (reportée en P8.8), mécanisme minimal proposé (P-1) :
   - lier depuis la session et délier exigent une **session créée il y a moins de 10 min** ; sinon `403 AUTH_REAUTH_REQUIRED` (« reconnectez-vous ») ;
   - lier exige un compte `active` et un **e-mail vérifié** ;
   - chaque liaison et déliaison envoie un **e-mail d'alerte** ;
   - le garde-fou `AUTH_LAST_SIGN_IN_METHOD` est conservé, sous verrou de ligne.
   - **Risque résiduel** : une session volée de moins de 10 min permet de lier le Google de l'attaquant. Voir §7, à inscrire dans les Known issues pour P8.8.
4. **Sécurité OAuth**
   - PKCE S256, `state` et `nonce`, à usage unique : flux dans Redis et cookie `cp_oauth_google`.
   - L'`id_token` est vérifié par `jose` avec le JWKS de Google (`iss`, `aud`, `exp`, `iat`, signature, `nonce`), car `arctic` décode sans vérifier.
   - E-mail accepté seulement si `email_verified` vaut vrai **et** si Google fait autorité sur l'adresse (P-2).
   - Délai maximal de 5 s, **aucune relance** : un code d'autorisation ne sert qu'une fois.
5. **Données** : aucune table, colonne, index ou RLS ajoutés.
   - `iam.user_identities` (`provider`, `provider_user_id`, `email`, `profile`, `last_used_at`, `UNIQUE (provider, provider_user_id)`) suffit.
   - Ce qu'elle n'a pas, et la parade :
     - pas de `public_id` → déliaison par fournisseur (`DELETE /identities/google`, P-5) ;
     - pas d'unicité `(user_id, provider)` → règle appliquée sous `SELECT … FOR UPDATE` de l'utilisateur ;
     - pas de RLS ni de droit `app_auth` → accès par `app_rw` en transaction, toujours filtré par `user_id` ; RLS par utilisateur reportée en P8.8.
   - Une migration de **données** : 7 codes d'erreur.
6. **Interface** :
   - bouton Google conforme à la charte (logo « G » officiel, « Continuer avec Google ») sur la connexion et l'inscription ;
   - écran G8 `/auth/link-account` ;
   - page G5 minimale `/account/security`, réduite à la seule section « Moyens de connexion » (P-4), que P8.8 complétera.
   - Note d'écart à ajouter dans `docs/maquettes.md` (texte exact au §4.6).

### 1.2 Propositions (aucune décision ✅ créée)

| Id | Proposition | Statut |
|---|---|---|

### 1.3 Hypothèses

- **H1** : `signup.mode` n'est pas appliqué aux inscriptions Google (P2.4), comme en P2.1 et P2.2.
- **H2** : organisation personnelle créée en `CM` / `XAF` / `eu-fr`, comme P2.1 (le fournisseur ne donne pas de pays fiable).
- **H3** : `compliance.legal_acceptances` n'est écrit par aucun parcours. La mention de la maquette 01 couvre l'inscription Google. Dette inchangée.
- **H4** : langue du compte créé = `locale` de la page (`fr` ou `en`, transmise à `start`). Le claim `locale` de Google est ignoré.
- **H5** : un compte créé par Google peut définir un mot de passe avec « Mot de passe oublié » (P2.1, inchangé). C'est son moyen d'obtenir une deuxième méthode avant de délier Google.
- **H6** : D-k (« la réinitialisation vérifie l'e-mail ») part en P8.8. En P2.3, la victime d'un pre-hijacking passe par : réinitialisation → connexion → renvoi de la vérification → vérification → liaison (CA-14).

### 3.3 Déroulé du rappel (`oauth.service.handleGoogleCallback`)

1. Lire le cookie et faire `GETDEL` du flux. Absent → `FLOW_INVALID`. Toujours effacer le cookie.
2. Paramètre `error` présent → `FLOW_INVALID` (`reason=cancelled` si `access_denied`), **aucun appel à Google**.
3. Comparer `state` en temps constant (`timingSafeEqual` sur des tailles égales). Écart → `FLOW_INVALID`, aucun appel.
4. Appeler `google.validateAuthorizationCode(code, code_verifier)` (`arctic`).
   - Délai maximal 5 s (constante typée, réglable par une couture de test).
   - **Aucune relance.**
   - Réseau, délai ou 5xx → `PROVIDER_UNAVAILABLE`.
   - `invalid_grant` ou autre 4xx → `FLOW_INVALID`.
5. Vérifier l'`id_token` avec `jwtVerify(idToken, JWKS, { issuer: ['https://accounts.google.com','accounts.google.com'], audience: GOOGLE_CLIENT_ID, algorithms: ['RS256'], clockTolerance: 60 })`.
   - JWKS : `createRemoteJWKSet(new URL('https://www.googleapis.com/oauth2/v3/certs'), { timeoutDuration: 5000 })`, en cache.
   - JWKS injoignable → `PROVIDER_UNAVAILABLE`.
   - Échec de vérification → `FLOW_INVALID`.
   - Puis : `nonce` égal (temps constant) ; `iat ≤ now+60 s` ; `sub` est une chaîne de 1 à 255 caractères.
6. Appliquer la règle e-mail (P-2) → sinon `EMAIL_UNVERIFIED`. Normaliser l'e-mail en minuscules.
7. Transaction `app_rw` + `pg_advisory_xact_lock(hashtext('oauth:google:'‖sub))` :
   - **identité connue** :
     - utilisateur supprimé → `SIGNUP_CLOSED` ;
     - utilisateur suspendu → `ACCOUNT_SUSPENDED` ;
     - intention `link` avec un autre utilisateur → `ALREADY_LINKED (sub_linked_elsewhere)` ;
     - intention `link` avec le même utilisateur → succès sans effet ;
     - sinon connexion : `last_used_at`, `email` de l'identité mis à jour, `last_login_at`, session. **`users.email` n'est jamais modifié.**
   - **intention `link`** :
     - la session du flux n'est pas révoquée et correspond au cookie de session reçu au rappel (même navigateur) ; sinon `FLOW_INVALID` ;
     - `FOR UPDATE` de l'utilisateur ; contrôles P-1 (c) ;
     - identité Google déjà présente → `ALREADY_LINKED (provider_already_linked)` ;
     - `INSERT` ;
     - e-mail d'alerte après le commit.
   - **e-mail inconnu** : `createUserWithOrgTx` (`active`, e-mail vérifié, `full_name` = `name` nettoyé (1 à 200 caractères, sans NUL, sinon NULL)) + identité + session.
   - **e-mail connu, compte supprimé** (`deleted_at` non nul) → `SIGNUP_CLOSED`.
   - **e-mail connu, autre cas** (`pending`, `active`, `suspended`) → **liaison en attente** : Redis + cookie `cp_link`, aucune écriture en base, redirection `?link=google`.
   - `23505` sur `users_email_key` (inscription e-mail concurrente) → même parcours que « e-mail connu ».
   - `23505` sur la contrainte `(provider, provider_user_id)` → impossible sous le verrou consultatif ; sinon `FLOW_INVALID`, journalisé. Les deux cas sont distingués par `constraint_name`.
8. Les jetons sont jetés en fin de requête (variable locale). Seuls `sub` et `email` sont gardés.
9. Redirection 302 vers l'origine `APP_URL` uniquement, avec `next` passé par `safeNextPath`.

## 7. Points d'attention

**Sécurité**

- **Risque résiduel P-1 (Known issue → P8.8)** : une session volée **de moins de 10 min**, ou un poste resté ouvert juste après une connexion, permet de lier le Google de l'attaquant. Il obtient alors un accès durable : la réinitialisation du mot de passe révoque les sessions mais pas l'identité.
  - Parades P2.3 : fraîcheur, e-mail vérifié, alerte e-mail avec lien vers `/account/security`, déliaison en libre-service (P-4).
  - Parade complète en P8.8 : ré-authentification forte, deuxième étape, audit.
- **IDOR** : aucune route ne prend un id d'identité. Toutes les requêtes filtrent sur l'utilisateur de la session. Pas de RLS sur `user_identities` (C2) : la RLS « par utilisateur » est reportée en P8.8 (défense en profondeur).
- **Redirection ouverte** : `safeNextPath` côté API (source de vérité) et côté front. Redirections absolues vers l'origine `APP_URL` seulement.
- **CSRF de connexion** : `state` lié au cookie de flux du navigateur, `GETDEL`, comparaison en temps constant (CA-9 : cookie d'un autre flux).
- **Énumération** : le rappel révèle « compte existant » seulement à la personne qui a prouvé, par Google, la maîtrise de l'adresse (P-2). `register` (P2.1) reste non discriminant.
- **Secret** : `GOOGLE_CLIENT_SECRET` dans Infisical (P8.1), jamais dans un journal ni une trace. Ligne à ajouter dans PROJECT_STATE (« À renseigner avant tout déploiement »).

**Production (Known issues)**
- Proxy Nuxt codé en dur (C13).
- Écran de consentement Google : nom provisoire `project-cp` (D21), domaine vérifié, URI de redirection de production.
- Éventuelle vérification de la marque par Google pour afficher le logo et le nom.

**Coûts et crédits** : aucun (l'authentification est gratuite).

**Garde-fous IA** : aucun appel de modèle.

**Performance**
- Rappel : 1 appel au point de jeton + JWKS en cache, au plus 5 s chacun.
- Requêtes indexées : `(provider, provider_user_id)` UNIQUE, `user_identities_user_idx`, `users.email` UNIQUE.
- Verrou consultatif par `sub`, de courte durée. Aucun appel réseau dans une transaction : l'échange et la vérification se font **avant** l'ouverture de la transaction.
- `/me` : une requête de plus (identités, indexée).
- `/methods` en cache 60 s.

**Cas limites**
- Un compte téléphone seul qui clique « Continuer avec Google » crée un **second compte** (aucun e-mail à rapprocher). Comportement attendu, documenté. La fusion de comptes se fait par l'assistance, hors produit.
- Deux comptes Google avec le même e-mail : un seul peut être lié par compte. Le second → `provider_already_linked`.

### A.4 Mécanique (rappels essentiels)

- **Vérification du ticket** : une transaction `app_rw` avec `app.user_id` posé.
  1. `SELECT … FOR UPDATE` par `token_hash`.
  2. Incrément de `attempts`.
  3. TOTP : secret lu dans le store **avant** la transaction, puis `UPDATE user_mfa_factors SET last_used_step=$s WHERE … AND (last_used_step IS NULL OR last_used_step < $s) RETURNING`.
  4. Code de secours : `UPDATE … SET used_at=now() WHERE user_id AND code_hash AND used_at IS NULL RETURNING`.
  5. Code faux : on **renvoie** un résultat, on valide la transaction, puis on lève l'erreur (piège P2.2).
  6. Code juste : `consumed_at`, session `mfa_passed=true`, `last_login_at`.
- **TOTP** : `@oslojs/otp` `generateHOTP` sur S−1, S et S+1, comparaison en temps constant, SHA-1, 6 chiffres, 30 s, secret de 20 octets en base32 (`@oslojs/encoding`), horloge injectable. Libellé = e-mail, sinon numéro masqué ; émetteur `brand.name`.
- **SecretStore** : `put` puis `INSERT`, avec compensation `delete`. Suppression : `DELETE` en base, puis suppression dans le store au mieux (orphelin journalisé).
- **WebAuthn** :
  - `rp.id = WEBAUTHN_RP_ID` ; `user.id` = handle de 32 octets ≠ `public_id` ; `attestation:"none"` ; `residentKey:"required"`, `userVerification:"required"` ; algorithmes -7 et -257 ; `excludeCredentials`.
  - Challenges dans Redis (300 s, `GETDEL`) : clé par session (enregistrement et ré-auth), par cookie `cp_webauthn` (connexion), par ticket (deuxième étape).
  - Compteur refusé si `stored > 0 && new <= stored` (alerte de clonage, clé gardée). 0/0 accepté.
  - Nom par défaut déduit de l'agent utilisateur. Android Chrome avec verrouillage d'écran, iOS 16+.
- **Apple** :
  - `arctic` `Apple` : `state` + `nonce` + `client_secret` = JWT ES256 (`kid=APPLE_KEY_ID`, `iss=TEAM_ID`, `sub=CLIENT_ID`, `aud=https://appleid.apple.com`, `exp ≤ iat + 6 mois`). PKCE seulement si `arctic` et Apple l'acceptent.
  - JWKS `https://appleid.apple.com/auth/keys`, `iss https://appleid.apple.com`.
  - `email_verified` et `is_private_email` en chaîne.
  - Nom pris dans le champ `user` du `form_post` (première autorisation seulement, ≤ 200 caractères, sans NUL).
  - Clé stable = `sub`. Relais privé → nouveau compte, jamais de rapprochement. `profile = {is_private_email}`.
  - Hors lot : notifications serveur à serveur d'Apple, révocation des jetons à la suppression (R5).
  - **Prérequis de production** : domaine vérifié chez Apple et domaine d'envoi d'e-mails enregistré dans le relais privé.
- **R2** :
  - Activité = `GREATEST(last_login_at, max(user_sessions.last_seen_at), created_at)`.
  - Compte téléphone avec un autre moyen, inactif → 403 `AUTH_MFA_REQUIRED` `{reason:"dormant_phone", methods:["password"]}`, sans ticket ni session, jeton OTP consommé, alerte e-mail.
  - Anti-énumération inchangée : révélé seulement après un bon code SMS.
  - D59 tient : aucun utilisateur créé.
- **`requireAuth`** : `users.mfa_enabled AND NOT session.mfa_passed` → 401.

### A.5 Critères d'acceptation P8.8 (condensés, numérotation d'origine)

**a — base**
- **A1 (SQL)** :
  - `purpose='mfa_challenge'` accepté, `'foo'` → 23514 ;
  - doublon de `(user_id, code_hash)` → 23505 ;
  - RLS self : 0 ligne vue de B, `UPDATE` / `DELETE` de B → 0 ligne, `INSERT` pour B refusé, 0 ligne sans `app.user_id` ;
  - `app_auth` : `INSERT` dans `user_recovery_codes` refusé.
- **A2 (SQL)** : `auth_security_settings()` = 90, défaut 90 si la clé est absente ou invalide, `EXECUTE` refusé à `PUBLIC`, `app_rw` ne lit pas le paramètre.
- **A3 (SQL)** : deux TOTP vérifiés → 23505 ; colonnes présentes ; `rollback` puis `up`.

**a — activation**
- **A4** : `setup` sans ré-auth → 403 `AUTH_REAUTH_REQUIRED` `{methods:["password"]}`.

- **A6** : un second `setup` supprime le facteur en attente.
- **A7** : `activate` : mauvais code → 422 ; bon code → 10 codes `XXXXX-XXXXX` (`no-store`), `mfa_enabled`, 10 hachages de 32 octets, autres sessions révoquées, session courante renouvelée (ancien cookie 401).
