# Spec P2.3 : Google et Apple, clés d'accès (WebAuthn), vérification en deux étapes TOTP et codes de secours, protection des numéros recyclés

## 1. Résumé

1. **Le lot est trop gros pour une taille M. Je recommande trois sous-lots dans cet ordre**, et non l'ordre proposé dans le brief :
   - **P2.3a** : socle de la vérification en deux étapes (étape intermédiaire sans session, TOTP, codes de secours, ré-authentification, page « Sécurité du compte », garde-fou du dernier moyen de connexion, alertes, numéros recyclés R2).
   - **P2.3b** : clés d'accès.
   - **P2.3c** : Google et Apple.
   - Raison : Google, Apple et les clés d'accès doivent tous passer par la porte de la deuxième étape. Si on la construit d'abord, on évite de reprendre deux parcours. R2 a besoin de seconds facteurs, donc il va avec a. Le plafond SMS (R1) part dans un **mini-lot séparé « P2.2c »**, obligatoire avant tout vrai fournisseur SMS.
2. **Aucune session complète avant la deuxième étape.** Un premier facteur réussi (mot de passe, code SMS, Google/Apple) sur un compte protégé renvoie `403 AUTH_MFA_REQUIRED` (code déjà au catalogue). La réponse pose un cookie `cp_mfa` limité à `/v1/auth/mfa`, valable 5 min, 5 essais, à usage unique. Ce ticket est stocké dans `iam.verification_tokens` sous un nouveau `purpose='mfa_challenge'`. La session (`mfa_passed=true`) n'est créée qu'à la fin de la deuxième étape, dans la même transaction.
3. **Pas de rattachement automatique d'un compte social.** Une identité Google/Apple inconnue dont l'e-mail correspond à un compte existant ne crée rien et ne connecte personne. La liaison se fait seulement après une connexion au compte existant (deuxième étape comprise), puis une confirmation explicite, ou depuis la page Sécurité avec une ré-authentification récente. Un compte non vérifié (`pending`) ne peut ajouter aucun moyen de connexion ni aucun facteur : c'est l'anti « pre-hijacking ». Avec le relais d'e-mail privé d'Apple, un nouveau compte est créé, identifié par le `sub` d'Apple. Les jetons des fournisseurs ne sont jamais conservés.
4. **Données** : trois migrations, une par sous-lot.
   - Deux nouvelles tables : `iam.user_recovery_codes` et `iam.user_webauthn_credentials`.
   - Colonnes : `user_mfa_factors.last_used_step`, `user_sessions.last_reauth_at`, `users.webauthn_user_handle`.
   - Un nouveau `purpose`, une fonction de lecture des paramètres de sécurité, une RLS « par utilisateur » sur les tables de facteurs et d'identités, et environ 11 codes d'erreur.
   - Le secret TOTP va dans un `SecretStore`, sur le modèle de `SmsProvider` : implémentation `local` chiffrée (dev et test, interdite en production) et `none` (production : 503 `AUTH_MFA_UNAVAILABLE`). L'implémentation Infisical arrive avec P8.1.
5. **R2 (numéros recyclés)** : après 90 jours sans activité (paramètre `security.phone_dormancy_days`), un code SMS seul ne suffit plus si le compte a un autre moyen (deuxième étape ou autre méthode de connexion). Pour un compte qui n'a que le téléphone, une décision de Dylan est nécessaire (§8, Q1). Les maquettes 04 et 09 relèvent de P2.7/P5.6 (consentement OAuth d'un client MCP), **pas** de P2.3.

## 3. Critères d'acceptation (TDD)

Couches :
- **U** : unitaire.
- **I** : intégration PostgreSQL + Redis réels ; le nom du `describe` contient « PostgreSQL réel ». `CP_REQUIRE_INTEGRATION=1` fait d'un saut un échec.
- **SQL** : `db/tests`.
- **R** : route via `app.request`.
- **C** : composant (`packages/ui`, D55).
- **E2E** : Playwright. « E2E réel » = API, PostgreSQL et Redis réels.

Les identifiants exposés sont toujours des `public_id`. Chaque test d'intégration crée **deux utilisateurs dans deux organisations** pour prouver l'isolation.

### P2.3a — Socle de la vérification en deux étapes

**Base de données**

- **CA-A1 (SQL)**
  - `verification_tokens` accepte `purpose='mfa_challenge'` et refuse `'foo'` (23514).
  - `user_recovery_codes` a `UNIQUE (user_id, code_hash)` ; un doublon donne 23505.
  - Sous `SET ROLE app_rw` avec `app.user_id=A` :
    - `SELECT` sur `user_mfa_factors` et `user_recovery_codes` de B → 0 ligne ;
    - `UPDATE` et `DELETE` de B → 0 ligne ;
    - `INSERT` avec `user_id=B` → refus RLS.
  - Sans `app.user_id` → 0 ligne.
  - `app_auth` : `INSERT` dans `user_recovery_codes` → `permission denied`.
- **CA-A2 (SQL)**
  - `platform.auth_security_settings()` renvoie `phone_dormancy_days=90` (valeur semée).
  - Elle renvoie aussi 90 si la clé est absente ou la valeur invalide : défaut sûr, jamais d'erreur 22P02.
  - `EXECUTE` : accordé à `app_rw` et `app_auth`, refusé à `PUBLIC`.
  - Sous `app_rw`, `SELECT … FROM platform.settings WHERE key='security.phone_dormancy_days'` → 0 ligne (preuve que la fonction est nécessaire).
- **CA-A3 (SQL)**
  - Index unique partiel : deux facteurs `totp` vérifiés pour un même utilisateur → 23505.
  - Un facteur vérifié et un facteur en attente sont acceptés.
  - `user_sessions.last_reauth_at` et `user_mfa_factors.last_used_step` existent.
  - `rollback` puis `up` repasse.

**Activation**

- **CA-A4 (I)**
  - Étant donné un utilisateur e-mail vérifié, connecté depuis plus de 10 min et sans ré-authentification,
  - quand il appelle `POST /v1/auth/mfa/totp/setup`,
  - alors 403 `AUTH_REAUTH_REQUIRED` avec `details.methods = ["password"]`.
- **CA-A5 (I)**
  - Étant donné le même utilisateur juste ré-authentifié (`POST /reauth` avec le mot de passe → 204, `last_reauth_at` non nul),
  - quand il appelle `setup`,
  - alors 200 `{ factor_id, otpauth_uri, secret }` avec `Cache-Control: no-store`.
    - URI : `otpauth://totp/project-cp:<libellé>?secret=…&issuer=project-cp&algorithm=SHA1&digits=6&period=30` ;
    - secret base32 de 32 caractères (160 bits).
  - En base : facteur `kind='totp'`, `verified_at NULL`, `secret_ref='users/<user_public_id>/mfa/totp/<factor_public_id>'`.
  - **Le secret n'apparaît dans aucune colonne** : recherche texte du secret dans `iam.*` → 0.
  - Dans Redis (store `local`), la valeur chiffrée existe et ne contient pas le secret en clair.
  - `users.mfa_enabled` reste `false`.
- **CA-A6 (I)**
  - Étant donné un facteur en attente, quand un second `setup` est appelé,
  - alors l'ancien facteur et son secret dans le store sont supprimés. Un seul facteur en attente.
- **CA-A7 (I)**
  - Étant donné un facteur en attente, quand `activate` reçoit un mauvais code,
  - alors 422 `AUTH_MFA_CODE_INVALID` et le facteur reste en attente.
  - Avec le bon code (calculé avec une horloge injectée), 200 `{ recovery_codes: [10] }` (format `XXXXX-XXXXX`, alphabet Crockford) et `Cache-Control: no-store`. En base :
    - `mfa_enabled = true` et `verified_at` non nul ;
    - 10 lignes `user_recovery_codes` dont `code_hash` vaut 32 octets et ne contient aucun code en clair ;
    - **les autres sessions** de l'utilisateur sont révoquées ;
    - **la session courante est renouvelée** : l'ancien cookie donne 401 sur `/me`, le nouveau 200, `mfa_passed = true`.
- **CA-A8 (I)**
  - Étant donné un facteur id appartenant à l'utilisateur B, quand A appelle `activate` avec cet id,
  - alors 404 `PLATFORM_RESOURCE_NOT_FOUND` et le facteur de B est intact.
- **CA-A9 (I)**
  - Étant donné un compte `pending` (P2.1, e-mail non vérifié), quand il appelle `setup`,
  - alors 403 `AUTH_ACCOUNT_NOT_VERIFIED`. Même chose dans P2.3b et P2.3c pour l'ajout d'une clé d'accès et la liaison sociale.

**Étape intermédiaire (aucune session complète)**

- **CA-A10 (I, test obligatoire « 2FA requise »)**
  - Étant donné un utilisateur dont la vérification en deux étapes est active, quand `POST /login` reçoit le bon mot de passe,
  - alors 403 `AUTH_MFA_REQUIRED` avec `details = { methods: ["totp","recovery_code"], reason: "mfa_enabled", expires_in_seconds: 300 }` (plus `"webauthn"` s'il a une clé d'accès, en P2.3b).
  - `Set-Cookie: cp_mfa=…; HttpOnly; SameSite=Strict; Path=/v1/auth/mfa; Max-Age=300` (plus `Secure` en production).
  - **Aucun `Set-Cookie` de session.** Le nombre de lignes `user_sessions` ne change pas.
  - Une ligne `verification_tokens` : `purpose='mfa_challenge'`, `user_id`, `max_attempts=5`, `expires_at` ≈ now()+300 s, `token_hash` = sha256 du ticket.
  - Avec un mauvais mot de passe, réponse 401 inchangée et aucun ticket.
- **CA-A11 (I)** : la valeur de `cp_mfa` envoyée comme cookie de session (`cp_session=<ticket>`) ou en `Authorization: Bearer` → `GET /me` donne 401. Un ticket n'est jamais une session.
- **CA-A12 (I, test obligatoire « connexion TOTP »)**
  - Étant donné le ticket, quand `POST /mfa/verify` reçoit `{ method:"totp", code, remember_me:true }` avec un code valide,
  - alors 200 avec la forme `authResponse`.
  - `Set-Cookie` de session (`Max-Age` « rester connecté »), `cp_mfa` effacé (`Max-Age=0`).
  - Session `mfa_passed=true`, ticket `consumed_at` non nul, `last_used_step = floor(t/30)`, `last_login_at` mis à jour.
- **CA-A13 (I, test obligatoire « anti-rejeu TOTP »)**
  - Étant donné un code accepté au pas S, quand une nouvelle connexion (nouveau ticket) renvoie le même code,
  - alors 422 `AUTH_MFA_CODE_INVALID` sans session.
  - Fenêtre : un code de S−1 est accepté si `last_used_step < S−1`. Un code de S+1 (dérive) est accepté. S−2 et S+2 sont refusés.
- **CA-A14 (I, concurrence)**
  - Deux `mfa/verify` simultanés sur le même ticket avec le bon code : exactement un 200, l'autre 422 (`AUTH_MFA_CHALLENGE_EXPIRED` ou `AUTH_MFA_CODE_INVALID`). Une seule session.
  - Deux tickets différents, même code, simultanés : un seul 200 (garde `last_used_step < $step` sous `FOR UPDATE`).
- **CA-A15 (I, test obligatoire « trop d'essais »)**
  - 5 codes faux donnent 422 `AUTH_MFA_CODE_INVALID` avec `remaining_attempts` = 4, 3, 2, 1, 0.
  - Le 6ᵉ essai, **avec le bon code**, donne 422 `AUTH_MFA_CHALLENGE_EXPIRED`. `attempts = 5`, jamais plus (incrément validé **avant** de lever l'erreur, même piège qu'en P2.2).
  - Ticket expiré (horloge de la base dépassée), absent ou déjà consommé → `AUTH_MFA_CHALLENGE_EXPIRED`.
- **CA-A16 (I)**
  - Limite par utilisateur : après 10 échecs en 15 min, même répartis sur plusieurs tickets, réponse 429 `PLATFORM_RATE_LIMIT` avec `Retry-After`.
  - La clé `rl:auth:mfa:user:<hmac>` existe dans Redis et ne contient ni e-mail ni id interne.
  - **Un seul** e-mail d'alerte « Tentatives de vérification échouées » par fenêtre (boîte Mailpit, ou transport de test).
- **CA-A17 (I, test obligatoire « code de secours à usage unique »)**
  - `mfa/verify {method:"recovery_code", code:"abcde fghjk"}` (casse et séparateurs normalisés) → 200 et `used_at` non nul.
  - Le même code réutilisé → 422 `AUTH_MFA_CODE_INVALID`.
  - Deux utilisations simultanées du même code → un seul succès.
  - `GET /security` → `recovery_codes_remaining: 9`. E-mail d'alerte « code de secours utilisé ».
- **CA-A18 (I)**
  - Défense en profondeur : une session `mfa_passed=false` d'un utilisateur `mfa_enabled=true` (insérée par le pool admin dans le test) → `GET /me` donne 401 `AUTH_TOKEN_INVALID`.
- **CA-A19 (I)**
  - Téléphone : pour un compte téléphone avec la vérification en deux étapes, `phone/verify-code` avec le bon code SMS → 403 `AUTH_MFA_REQUIRED` avec `cp_mfa`, sans session. Le jeton OTP est consommé. Puis TOTP → session.
- **CA-A20 (I)** : réinitialiser le mot de passe ne contourne pas la deuxième étape. Après `reset-password`, `login` → 403 `AUTH_MFA_REQUIRED`. D-k : `email_verified_at` est rempli après la réinitialisation.

**Gestion**

- **CA-A21 (I)**
  - `POST /mfa/recovery-codes/regenerate` exige une ré-authentification (sinon 403 `AUTH_REAUTH_REQUIRED`).
  - Après régénération, les 10 anciens codes ne marchent plus et les 10 nouveaux oui.
  - Les codes sont renvoyés une seule fois ; `GET /security` ne les renvoie jamais.
- **CA-A22 (I)**
  - `DELETE /mfa/totp` après une ré-authentification par **mot de passe seulement** → 403 `AUTH_REAUTH_REQUIRED` avec `details.methods: ["totp","webauthn"]`.
  - Après ré-authentification par TOTP (moins de 10 min) → 204. Le facteur, son secret dans le store et les codes de secours sont supprimés, `mfa_enabled=false`.
  - E-mail d'alerte et notification in-app. La connexion suivante se fait sans étape.
- **CA-A23 (I)**
  - `POST /reauth {method:"password"}` avec un mauvais mot de passe → 401 `AUTH_INVALID_CREDENTIALS`, compté dans la limite par utilisateur.
  - Une ré-authentification vieille de plus de 10 min ne compte plus.
  - Une session créée il y a moins de 10 min compte comme ré-authentifiée seulement quand aucun facteur fort n'est exigé (D-f).
- **CA-A24 (I)**
  - `GET /security` renvoie :
    - `{ mfa: { enabled, recovery_codes_remaining }, password: bool, phone: { masked } | null, identities: [], passkeys: [], sign_in_methods: n }` ;
    - aucun `secret_ref`, aucun hachage, aucun id interne.
  - Sous le contexte de A, rien de B n'apparaît.
- **CA-A25 (U + I)**
  - `countSignInMethods(user)` = mot de passe (e-mail **et** `password_hash`) + téléphone vérifié + identités + clés d'accès.
  - Le TOTP n'est **pas** un moyen de connexion.
  - Le calcul se fait sous `SELECT … FROM iam.users WHERE id=$1 FOR UPDATE` (sérialisation ; prouvée en b et c).

### P2.3b — Clés d'accès (WebAuthn)

- **CA-B1 (SQL)**
  - `user_webauthn_credentials` : `credential_id` UNIQUE, `name` de 1 à 64 caractères, `sign_count ≥ 0`, `device_type IN ('singleDevice','multiDevice')`.
  - RLS par utilisateur (mêmes contrôles que CA-A1) ; `app_auth` a `SELECT` seulement.
  - `users.webauthn_user_handle` UNIQUE, 32 octets (CHECK sur la longueur).
- **CA-B2 (I)**
  - `POST /passkeys/registration/options` exige une ré-authentification.
  - Contenu des options :
    - `rp.id = WEBAUTHN_RP_ID` et `rp.name` ;
    - `user.id` = `webauthn_user_handle` : 32 octets aléatoires créés une seule fois, **différents du `public_id`** ;
    - `attestation: "none"` ;
    - `authenticatorSelection = { residentKey:"required", userVerification:"required" }` ;
    - `pubKeyCredParams` contient -7 et -257 ;
    - `excludeCredentials` = les clés déjà enregistrées.
  - Challenge dans Redis `auth:webauthn:reg:<session_public_id>`, TTL ≤ 300 s.
- **CA-B3 (I, authentificateur logiciel de test)**
  - `POST /passkeys {response, name?}` → 201 `{ id, name, created_at, last_used_at:null, backed_up, device_type }`, ligne en base, challenge supprimé (`GETDEL`).
  - Chacun de ces cas → 422 `AUTH_PASSKEY_INVALID` sans ligne :
    - mauvaise origine ;
    - mauvais `rpIdHash` ;
    - challenge rejoué ;
    - indicateur UV absent ;
    - `credential_id` déjà enregistré.
  - 11ᵉ clé → 409 `PLATFORM_CONFLICT` (`details.reason:"passkey_limit"`, limite 10).
- **CA-B4 (I, test obligatoire « connexion par clé d'accès »)**
  - `POST /passkeys/authentication/options` est public : pas d'`allowCredentials`, cookie `cp_webauthn` (HttpOnly, SameSite=Strict, 300 s).
  - `verify` → 200 avec session `mfa_passed=true`, **sans** deuxième étape même si elle est active (D-h). `sign_count` et `last_used_at` sont mis à jour.
- **CA-B5 (I)** — même réponse 422 `AUTH_PASSKEY_INVALID`, corps identique, aucune session, dans chacun de ces cas :
  - `credential_id` inconnu ;
  - clé supprimée ;
  - `userHandle` qui ne correspond pas au propriétaire de la clé ;
  - challenge venant d'un autre navigateur (cookie absent ou différent) ;
  - challenge expiré ou rejoué.
  - Utilisateur `suspended` → 403 `AUTH_ACCOUNT_SUSPENDED`.
- **CA-B6 (I)**
  - Clonage : compteur stocké à 10, assertion à 5 → 422, alerte `passkey_clone_suspected` (e-mail et notification), clé conservée.
  - Les compteurs 0 / 0 (clés synchronisées) sont acceptés.
- **CA-B7 (I)**
  - Clé d'accès comme deuxième étape : `login` → 403 avec `methods` contenant `"webauthn"`.
  - `mfa/webauthn/options` (ticket requis) → `allowCredentials` = les clés **de ce seul utilisateur**. `verify` → session.
  - Une clé d'un autre utilisateur → 422.
- **CA-B8 (I)**
  - `PATCH /passkeys/{id}` : nom de 1 à 64 caractères, NUL refusé (422).
  - L'id d'un autre utilisateur → 404 et sa ligne est intacte.
- **CA-B9 (I, test obligatoire « dernier moyen de connexion »)**
  - Un utilisateur dont le seul moyen est une clé d'accès (compte créé par téléphone puis numéro détaché en base pour le test, ou compte social de P2.3c) : `DELETE /passkeys/{id}` → 409 `AUTH_LAST_SIGN_IN_METHOD`.
  - **Concurrence** : avec exactement deux moyens (clé + identité Google), deux suppressions simultanées donnent exactement un 204 et un 409 ; il reste un moyen.
- **CA-B10 (I)** : suppression d'une clé → ré-authentification exigée, alerte `passkey_removed`. La deuxième étape ne propose plus `webauthn` s'il ne reste aucune clé.
- **CA-B11 (E2E réel, authentificateur virtuel Chromium via CDP `WebAuthn.addVirtualAuthenticator`, `hasUserVerification:true`)**
  - Enregistrer une clé sur `/account/security`, se déconnecter, « Utiliser une clé d'accès » → accueil. Desktop et mobile émulé.
- **CA-B12 (C / E2E)**
  - Sans `window.PublicKeyCredential`, les boutons de clé d'accès sont masqués.
  - Annulation par l'utilisateur (`NotAllowedError`) → message neutre « Opération annulée », pas d'alerte d'erreur.

### P2.3c — Google et Apple (faux fournisseur OIDC : MSW, jetons signés par une clé `jose` de test, `onUnhandledRequest:'error'`)

- **CA-C1 (I)** — `GET /oauth/google/start?next=/account/security` → 302 vers `accounts.google.com`, avec :
  - `response_type=code`, `client_id` ;
  - `redirect_uri` **exactement** égal à `${APP_URL}/v1/auth/oauth/google/callback` ;
  - `scope=openid email profile` ;
  - `state` d'au moins 43 caractères, `code_challenge_method=S256`, `nonce`.
  - `Set-Cookie: cp_oauth_google` (HttpOnly, SameSite=Lax, Path=/v1/auth/oauth/google, Max-Age=600).
  - Redis : la clé de flux existe avec un TTL ≤ 600 et ne contient aucune PII.
  - `next=//evil.com`, `next=https://evil.com` ou `next=/\evil` → `next` ramené à `/` (pas de redirection ouverte).
- **CA-C2 (I, test obligatoire « inscription Google »)**
  - Rappel avec un `code` valide (MSW : jeton + JWKS ; `id_token` avec `email_verified:true`) → 302 vers `next` avec cookie de session.
  - Utilisateur créé :
    - `email` = celui du jeton, `email_verified_at` non nul, `status='active'`, `password_hash NULL`, `full_name` = `name` ;
    - organisation personnelle créée (fonction 0003) ;
    - ligne `user_identities (google, sub, email)`.
  - **Aucun jeton d'accès ni de rafraîchissement stocké** (recherche des valeurs MSW dans tout `iam.*` → 0).
  - La clé de flux est supprimée.
- **CA-C3 (I, test obligatoire « PKCE »)** : MSW vérifie que `S256(code_verifier)` reçu par le point de jeton est égal au `code_challenge` émis au départ.
- **CA-C4 (I, test obligatoire « state / flux invalide »)**
  - Cas : state différent ; cookie de flux absent ; flux expiré ; même rappel rejoué une deuxième fois ; paramètre `error=access_denied`.
  - Chacun → 302 `/auth/login?error=AUTH_SOCIAL_FLOW_INVALID`.
  - **Le point de jeton n'est jamais appelé** (espion MSW). Aucun utilisateur.
- **CA-C5 (I, test obligatoire « id_token invalide »)**
  - Cas : `nonce` différent, `aud` étrangère, `iss` étranger, `exp` passé, `iat` dans le futur de plus de 5 min, signature d'une autre clé, `alg:none`.
  - Chacun → `AUTH_SOCIAL_FLOW_INVALID` sans utilisateur.
- **CA-C6 (I)** : `email_verified:false` → 302 `?error=AUTH_SOCIAL_EMAIL_UNVERIFIED` sans utilisateur.
- **CA-C7 (I, test obligatoire « connexion Google »)**
  - Identité connue → session pour le même utilisateur, `last_used_at` mis à jour, e-mail de l'identité rafraîchi. **`users.email` n'est jamais modifié.**
  - Si la deuxième étape est active → 302 `/auth/two-factor` avec `cp_mfa` et sans session.
- **CA-C8 (I, test obligatoire « pas de rattachement automatique »)**
  - Étant donné un compte A (e-mail vérifié, mot de passe) et une identité Google inconnue portant le même e-mail (casse différente),
  - quand le rappel arrive,
  - alors aucune identité ni session n'est créée. 302 `/auth/login?error=AUTH_SOCIAL_ACCOUNT_EXISTS` + cookie `cp_link` (HttpOnly, SameSite=Lax, 600 s) + liaison en attente dans Redis `{provider, sub, email}`.
  - Suite : connexion par mot de passe (+ deuxième étape) → `GET /link/pending` → `{ provider:"google", email_masked }` → `POST /link/confirm` → 204. L'identité est rattachée à A, alerte `identity_linked`.
  - Sans confirmation, rien n'est rattaché. Après 10 min, `confirm` → 404.
- **CA-C9 (I)**
  - `POST /link/confirm` par un **autre** utilisateur B connecté portant le cookie `cp_link` → 404 (l'e-mail de la liaison doit être celui de l'utilisateur courant). Aucun rattachement.
- **CA-C10 (I, pre-hijacking)**
  - Un compte `pending` créé par un tiers avec l'e-mail de la victime, puis rappel Google de la victime avec ce même e-mail → même parcours que CA-C8 (rien n'est rattaché).
  - Ce compte `pending` connecté appelle `POST /oauth/google/link` → 403 `AUTH_ACCOUNT_NOT_VERIFIED`.
  - La victime fait « mot de passe oublié » puis réinitialise : sessions du tiers révoquées, e-mail vérifié (D-k), liaison possible ensuite.
- **CA-C11 (I, test obligatoire « Apple form_post »)**
  - `POST /oauth/apple/callback` en `application/x-www-form-urlencoded` avec `Origin: https://appleid.apple.com` et le cookie `cp_oauth_apple` (`SameSite=None; Secure`) → 302 avec succès, **pas** de 403 CSRF.
  - Le même POST sans cookie de flux → `AUTH_SOCIAL_FLOW_INVALID`.
  - Les autres routes de `/v1/auth` restent protégées par le CSRF (régression P2.2).
- **CA-C12 (I, test obligatoire « relais privé Apple »)**
  - Première autorisation avec `user={"name":{"firstName":"Awa","lastName":"Nkeng"}}` et un e-mail `x1y2@privaterelay.appleid.com` (`is_private_email:"true"`, `email_verified:"true"` en chaîne) → nouveau compte, `full_name="Awa Nkeng"`, identité dont `profile = {is_private_email:true}`.

- **CA-C13 (U)**
  - `client_secret` Apple : JWT ES256, `kid = APPLE_KEY_ID`, `iss = TEAM_ID`, `sub = CLIENT_ID`, `aud = https://appleid.apple.com`, `exp ≤ iat + 6 mois`.

  - Identité déjà rattachée à X, et Y (connecté, ré-authentifié) lance la liaison avec le même `sub` → 302 vers la page Sécurité avec `?error=AUTH_IDENTITY_ALREADY_LINKED`. Rien ne change.
  - Une deuxième identité Google pour le même utilisateur → même code (index unique).
- **CA-C15 (I, concurrence)** : deux rappels simultanés pour le même nouveau `sub` (deux flux) → exactement un utilisateur. Le second rappel connecte au même utilisateur (23505 associé par nom de contrainte, une seule nouvelle tentative).
- **CA-C16 (I)**
  - Fournisseur lent (MSW avec un délai de plus de 5 s) ou en erreur 5xx → `?error=AUTH_SOCIAL_PROVIDER_UNAVAILABLE` sans utilisateur.
  - E-mail d'un compte `deleted` → `?error=AUTH_SIGNUP_CLOSED`.
- **CA-C17 (I)**
  - `DELETE /identities/{id}` : ré-authentification exigée.
  - Pour un compte uniquement social → 409 `AUTH_LAST_SIGN_IN_METHOD`.
  - Avec un téléphone vérifié → 204 et alerte `identity_unlinked`. L'id d'un autre utilisateur → 404.
- **CA-C18 (U / R)**
  - Configuration partielle (`GOOGLE_CLIENT_ID` sans secret) → `getEnv()` lève une erreur.
  - Aucune configuration → `GET /methods` renvoie `google:false`, et `/oauth/google/start` → 302 `?error=AUTH_SOCIAL_PROVIDER_UNAVAILABLE`.
  - `GET /methods` → `{ password:true, phone:<SMS disponible>, passkey:true, google, apple }`.
- **CA-C19 (I)** : journaux sur tout P2.3c sans `code`, `state`, `nonce`, `id_token`, e-mail ni `sub` en clair (`sub` → HMAC tronqué si besoin de corrélation).
- **CA-C20 (E2E, API simulée)**
  - Boutons Google et Apple de connexion et d'inscription actifs selon `/methods`.
  - `?error=<CODE>` affiché en i18n.
  - Écran `/auth/link-account` (G8) : Lier / Annuler.
  - Pas d'aller-retour réel vers Google ou Apple dans les tests.

### Transverse

- **CA-T1 (CI)**
  - La suite d'intégration passe en `env -i` avec **uniquement** les variables de l'étape CI (§7) : 0 échec, 0 saut.
  - `NODE_ENV=production` sans `WEBAUTHN_RP_ID`, avec `SECRET_STORE_PROVIDER=local`, ou avec une configuration Apple partielle → démarrage refusé, message sans aucune valeur.
- **CA-T2 (R, régression)** : les tests P2.1 et P2.2 existants (unitaires, routes, 10 + N intégration) restent verts. `/me` est additif.

### 5.4 Ticket de deuxième étape et ré-authentification

- **Ticket** : 32 octets aléatoires (hex), dans le cookie `cp_mfa` seulement, jamais dans le corps.
  - `verification_tokens(purpose='mfa_challenge', user_id, target=user_public_id, token_hash=sha256(ticket), max_attempts=5, expires_at=now()+5 min, ip)`.
  - Un nouveau ticket expire les tickets actifs du même utilisateur, sous verrou consultatif, comme `issueOtpToken`.
- **Vérification** : une seule transaction `app_rw` avec `set_config('app.user_id')` :
  1. `SELECT … FOR UPDATE` du ticket par `token_hash` ; refus si consommé, expiré ou `attempts ≥ max`.
  2. Incrément de `attempts`.
  3. Vérification du facteur :
     - TOTP : lecture du secret dans le store **avant** la transaction (aucun appel réseau dans une transaction, cp-performance), puis `UPDATE user_mfa_factors SET last_used_step=$s, last_used_at=now() WHERE id=$f AND (last_used_step IS NULL OR last_used_step < $s) RETURNING id` ;
     - code de secours : `UPDATE … SET used_at=now() WHERE user_id AND code_hash AND used_at IS NULL RETURNING`.
  4. Code faux : **retour d'un résultat**, commit, puis le service lève l'erreur (piège P2.2).
  5. Code juste : `consumed_at`, `INSERT user_sessions (mfa_passed=true)`, `last_login_at`.
- **Ré-authentification** : `user_sessions.last_reauth_at = now()`.
  - Fenêtre de 10 min (`REAUTH_WINDOW_SECONDS`, constante typée).
  - « Ré-auth forte » = TOTP ou clé d'accès (exigée pour `DELETE /mfa/totp`).
  - Sans facteur fort chez l'utilisateur : `max(created_at, last_reauth_at) > now() − 10 min` suffit (D-f).
- `requireAuth` lit `mfa_passed`, `last_reauth_at` et `created_at` (pool `app_auth`, colonnes ajoutées à `findSessionByTokenHash`), ainsi que `users.mfa_enabled` (ajouté à `findUserById`).

### 5.5 TOTP et codes de secours

- **TOTP**
  - `@oslojs/otp` : `generateHOTP(key, counter, 6)` pour les pas S−1, S et S+1, comparés en temps constant.
  - SHA-1, 6 chiffres, 30 s : compatibilité Google Authenticator, Microsoft Authenticator, Aegis, 1Password.
  - Horloge injectable (`clock.now()`) pour les tests.
  - Secret de 20 octets, base32 sans remplissage (`@oslojs/encoding`).
  - Libellé du compte dans l'application : e-mail, sinon numéro masqué. Émetteur = `brand.name`.
- **Codes de secours**
  - 10 codes de 10 caractères Crockford (environ 50 bits chacun), affichés `XXXXX-XXXXX`.
  - Haché : `HMAC-SHA256(OTP_PEPPER, "recovery" ‖ user_public_id ‖ code_normalisé)`.
  - **Pourquoi pas argon2** : une entropie de 50 bits est hors de portée d'une attaque par force brute hors ligne quand le pepper est hors base, et l'accès en ligne est limité (ticket de 5 essais + limite par utilisateur). Avec argon2 et un sel, il faudrait aussi vérifier jusqu'à 10 hachages lents à chaque essai (environ 0,5 s CPU), ce qui ouvre un déni de service facile.
  - Comparaison par recherche directe de `(user_id, code_hash)`.
- **SecretStore** (`apps/api/src/modules/auth/secrets/`)
  - Interface : `interface SecretStore { readonly name; isAvailable(): boolean; put(path, value): Promise<void>; get(path): Promise<string|null>; delete(path): Promise<void> }`.
  - `LocalSecretStore` : Redis `devsecret:<path>`, AES-256-GCM, clé `SECRET_STORE_LOCAL_KEY` (32 octets base64), interdit en production (env + constructeur).
  - `UnavailableSecretStore` : `isAvailable()=false`.
  - Fabrique et coutures de test identiques à `sms.factory.ts`.
  - **Ordre d'écriture** : `put` dans le store, puis `INSERT` du facteur. En cas d'échec de l'`INSERT`, compensation `delete`. Pour la suppression : `DELETE` en base, puis suppression dans le store au mieux, un orphelin étant toléré et journalisé.

### 5.6 Connexion Google et Apple (P2.3c)

1. `start` : `state`, `nonce` et, pour Google seulement, `codeVerifier`, chacun de 32 octets.
   - Redis `auth:oauth:flow:<flowId>` = `{provider, state, nonce, codeVerifier?, intent:'login'|'link', userId?, next}` avec EX 600.
   - Cookie `cp_oauth_<provider>=<flowId>`. URL par `arctic` (`google.createAuthorizationURL(state, verifier, ['openid','email','profile'])` + `nonce` ajouté ; `apple.createAuthorizationURL(state, ['name','email'])` + `response_mode=form_post` + `nonce`).
2. Rappel : `GETDEL` du flux par le cookie (usage unique), puis `state` comparé en temps constant. En cas d'écart, **aucun appel au fournisseur**.
3. `validateAuthorizationCode(code[, verifier])`, borné à 5 s (`Promise.race` / `AbortSignal` selon ce que permet `arctic`).
4. `id_token` vérifié avec `jose.jwtVerify` et `createRemoteJWKSet` (Google `https://www.googleapis.com/oauth2/v3/certs`, Apple `https://appleid.apple.com/auth/keys`, mis en cache), `issuer` (Google : `https://accounts.google.com` ou `accounts.google.com` ; Apple : `https://appleid.apple.com`), `audience`, tolérance de 60 s. Puis `nonce` égal à celui stocké et `email_verified` à `true` (booléen ou chaîne).
5. Décision dans une transaction `app_rw` :
   - identité `(provider, sub)` connue → connexion (ou ticket de deuxième étape) ;
   - `intent=link` → vérifier le compte et la ré-authentification de `userId`, puis rattacher (409 si le `sub` est déjà rattaché) ;
   - sinon, e-mail inconnu → création (utilisateur + organisation personnelle + identité, `iam.create_personal_organization`) ;
   - e-mail connu → **liaison en attente** (Redis `auth:oauth:link:<linkId>` 600 s + cookie `cp_link`), jamais de rattachement ;
   - compte supprimé → `AUTH_SIGNUP_CLOSED`.
6. Les jetons du fournisseur sont jetés en fin de requête (ni base, ni Redis, ni journal).
7. Redirection 302 vers l'origine `APP_URL` uniquement, `next` validé par `^/(?!/|\\)`.

Apple : le nom vient du champ `user` du `form_post`, seulement à la première autorisation. On le conserve à la création ; ensuite on l'ignore et on ne fait jamais confiance à son contenu (longueur ≤ 200, NUL refusé). L'e-mail Apple peut changer ou disparaître : la clé stable est le `sub`.

**Hors lot** (Known issues avant la production) :
- point de notifications serveur à serveur d'Apple (consentement retiré, compte supprimé, relais désactivé) ;
- révocation des jetons Apple à la suppression du compte (R5).

### 5.7 Clés d'accès (P2.3b)

- **Options**
  - RP ID = `WEBAUTHN_RP_ID` ; origines attendues = `[origin(APP_URL)]`.
  - Challenge : Redis TTL 300 s, `GETDEL`. Clé par session pour l'enregistrement et la ré-authentification ; clé par cookie `cp_webauthn` (flux) pour la connexion ; clé par ticket pour la deuxième étape.
- **Vérification** : `verifyRegistrationResponse` / `verifyAuthenticationResponse` avec `requireUserVerification: true`.
- **Compteur** : refus si `stored > 0 && new <= stored`.
- **Nom par défaut** : « Clé d'accès » + appareil déduit de l'agent utilisateur (« Chrome sur Android ») ; renommable.
- **Connexion sans identifiant** : `userHandle` → `users.webauthn_user_handle` ; la clé doit appartenir à cet utilisateur, sinon 422 générique.
- **Compatibilité mobile** : Android (Chrome avec verrouillage d'écran) et iOS 16+ Safari. Les appareils sans verrouillage d'écran ne font pas d'UV : clé d'accès indisponible, les autres méthodes restent.

### 5.8 Rôles

| Rôle | Usage |
|---|---|
| `app_auth` | Lecture seule : sessions (avec `mfa_passed`, `last_reauth_at`), utilisateurs (avec `mfa_enabled`), identités (recherche par `sub`), clés d'accès (recherche par `credential_id`), blocklist, `auth_security_settings()` |
| `app_rw` | Toutes les écritures, en transaction, avec `app.user_id` posé (RLS par utilisateur) |
| `app_admin` | Jamais dans `apps/api/src` (règle 23 du garde-fou), seulement dans les tests |

### 5.9 R1 : plafond SMS (mini-lot P2.2c, recommandé hors P2.3)

- **Argument** : P2.3 n'envoie aucun nouveau SMS, puisque le SMS n'est pas un second facteur (D-h). R1 est indépendant, petit, et **bloquant avant tout vrai fournisseur**. On le traite à part pour ne pas alourdir un lot critique.
- **Périmètre minimal** :
  - Compteurs Redis atomiques `sms:day:<AAAAMMJJ>:<pays>` et `sms:day:<AAAAMMJJ>:all` (Lua `INCR` + `EXPIRE` 48 h), vérifiés avant l'envoi.
  - Plafonds dans `platform.rate_limit_policies` (clé `sms.daily`, `scope_type='global'`, `limits = {"per_day": N, "per_country": {"CM": n, …}}`). La table est lisible par `app_rw` ; cache de 60 s.
  - Plafond atteint : **503 `AUTH_SMS_UNAVAILABLE`, identique quel que soit le numéro** (pas d'énumération). Le jeton est compensé, comme en D61.
  - Alerte pino `error` `sms_daily_cap_reached` + journal d'avertissement à 80 % (Grafana en P8). Le plafond est aussi un coupe-circuit, sans relance automatique.
  - Plancher de temps de réponse inchangé.
