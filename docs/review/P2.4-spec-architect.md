# Spec P2.4 : organisations, workspaces, environnements (dont sandbox), rôles système, invitations, transfert d'Owner, application de `signup.mode` et de R4

## 0. Résumé (5 lignes)

1. **Aucune nouvelle table.** `iam.organizations`, `memberships`, `roles`, `role_permissions`, `invitations`, `workspaces` et `environments`, ainsi que `ux.user_preferences`, `billing.credit_wallets`, `dev.idempotency_keys` et `audit.events` existent déjà. Il faut deux migrations : 0005 (codes, grants, triggers « au moins un Owner » et « rôle de la même organisation », fonction `iam.create_organization` qui porte R4, portefeuilles) et 0006 (index `CONCURRENTLY`).
2. **Contexte d'organisation par l'URL.** `/v1/organizations/{organization_id}/…` pour ce qui dépend de l'organisation, `/v1/workspaces/{workspace_id}/…` et `/v1/environments/{environment_id}` pour le reste. Un middleware `orgContext` résout l'appartenance (pool `app_auth`). Un non-membre reçoit 404. Les droits viennent des permissions `iam.permissions` du seed, jamais du nom du rôle.
3. **Invitations.** Valables 7 jours. Jeton de 256 bits haché en SHA-256. Une seule invitation en attente par e-mail et par organisation (index existant ; une invitation expirée est révoquée automatiquement). L'invitation s'accepte par un utilisateur connecté dont l'e-mail correspond, ou par une inscription liée à l'invitation, sans organisation personnelle. Elle passe outre `waitlist` et `invite_only`, jamais `closed`.
4. **« Au moins un Owner » garanti en base.** Un trigger de contrainte différé verrouille la ligne de l'organisation. Le transfert d'Owner est atomique, réservé à un Owner, confirmé par la saisie du nom de l'organisation, audité et notifié par e-mail.
5. **`signup.mode` et R4.**
   - `signup.mode` est appliqué à l'inscription e-mail (P2.1), téléphone (P2.2) et à la création d'organisation, au moyen d'un `assertSignupAllowed()` partagé (à réutiliser en P2.3). En mode fermé, la réponse est identique pour toutes les adresses (pas d'énumération).
   - R4 (au plus une organisation Free possédée par utilisateur) est imposée dans la fonction SQL `iam.create_organization`, sous verrou consultatif.

## 3. Décisions de conception

### 3.1 Contexte d'organisation (D-f)

- **Routes de l'organisation** : `/v1/organizations/{organization_id}/…` (membres, invitations, workspaces, réglages, transfert).
- **Routes d'un workspace** : `/v1/workspaces/{workspace_id}…` et `/v1/environments/{environment_id}`. Ce modèle est celui de cp-hono (`/v1/workspaces/{workspaceId}/agents`) : l'organisation se déduit de la ressource.
- **Middleware `orgContext`**, placé après `requireAuth` :
  - il résout le `public_id` (organisation, ou workspace puis organisation, ou environnement puis workspace puis organisation) avec le pool `app_auth`, qui a déjà SELECT sur `organizations`, `workspaces`, `environments` et `memberships` ;
  - il charge l'appartenance `(organization_id, user_id)`.
- **Refus** :
  - Organisation inexistante, non-membre ou appartenance `suspended` → **404 `PLATFORM_RESOURCE_NOT_FOUND`**.
  - Organisation `suspended` → 403 `AUTH_ORGANIZATION_SUSPENDED`.
  - Organisation `pending_deletion` : lectures autorisées ; écritures → 409 `PLATFORM_CONFLICT` `{reason:'organization_pending_deletion'}`.
  - Workspace `suspended` → 403 `AUTH_WORKSPACE_SUSPENDED` ; workspace `archived` : écritures → 409 `{reason:'workspace_archived'}`.
  - Organisation id 0 → toujours 404 (T16).
- **Permissions** : `role_id` → cache mémoire des rôles système et de leurs permissions, chargé avec `app_rw` (catalogue lisible) et invalidé au redémarrage. Un `role_id` inconnu du cache (rôle personnalisé, P9) → refus, jamais d'autorisation par défaut.
- **Contexte posé** : `OrgAuthContext = AuthContext & { orgId, orgPublicId, membershipId, roleKey, permissions: ReadonlySet<string>, orgStatus, workspaceId?, environmentId? }`. Les ids internes restent côté serveur.
- **Transactions** : toutes les requêtes métier passent par `withOrgContext({orgId, userId})`.
- **Nouveau `withUserContext({userId})`** dans `packages/db` : il ne pose que `app.user_id`. Il sert à `GET /v1/organizations` (policies `membership_self_read` et `org_member_read`) et aux préférences (`prefs_self`).

### 3.2 `signup.mode` (D-b) : module partagé `apps/api/src/modules/auth/signup-policy.ts`

- `getSignupMode()` : lit `platform.settings` (`app_rw`, sans contexte), garde la valeur en cache 30 s. Une valeur inconnue ou mal formée donne `closed` (refus par défaut) et un log `warn` (Q7).
- `assertSignupAllowed({ via: 'email' | 'phone' | 'google' | 'invitation' | 'organization' })` :

| Mode | e-mail / téléphone / Google (nouveau compte) | invitation (accept-signup) | nouvelle organisation (`POST /v1/organizations`) | connexion d'un compte existant |
|---|---|---|---|---|
| `open` | ✓ | ✓ | ✓ (R4) | ✓ |
| `waitlist` | 403 `AUTH_SIGNUP_CLOSED` `{mode:'waitlist'}` | ✓ | 403 | ✓ |
| `invite_only` | 403 `{mode:'invite_only'}` | ✓ | 403 (Q5) | ✓ |
| `closed` | 403 `{mode:'closed'}` | 403 (Q4) | 403 | ✓ |

- **P2.1 `register`** : le contrôle se fait **avant** la recherche de l'e-mail. En mode fermé, la réponse est donc la même pour un e-mail connu ou inconnu, et le mode est une information publique. `verify-email`, `login` et `forgot-password` ne changent pas.
- **P2.2** : `request-code` ne change pas (aucune recherche, et la connexion reste possible). Dans `verify-code`, un numéro inconnu avec un mode autre que `open` donne 403 `AUTH_SIGNUP_CLOSED`. Le code reste consommé (commit), comme la règle du pays dans `signInOrSignUp`. Le contrôle se fait **dans** la transaction, juste avant `createUserWithOrgTx`.
- **P2.3 (Google)** doit appeler `assertSignupAllowed({via:'google'})` : à reporter dans la spec P2.3 (lot parallèle, D66).

### 3.3 R4 et création d'organisation (D-a)

- **Free** = organisation sans souscription vivante (`trialing, active, past_due, grace`) dont le plan a `tier > 0`.
- **Règle** : un utilisateur possède (rôle Owner actif) **au plus 1** organisation Free dont le statut n'est pas `deleted`.
- **Où la règle s'applique** :
  - seulement à `POST /v1/organizations`, par la fonction SQL `iam.create_organization` (§4) ;
  - l'inscription crée la première organisation (personnelle) ;
  - un utilisateur créé par invitation n'en a aucune (Q3) et peut en créer une si le mode est `open`.
- **Refus** : `BILLING_PLAN_LIMIT_REACHED` `{limit:'free_organizations_per_user', max:1}`.
- **Le transfert d'Owner n'est pas restreint par R4** (Q10). Il ne crée aucun crédit, et chaque organisation Free reçue correspond à un numéro vérifié distinct.
- **Onboarding « entreprise » (P2.5, maquette 18)** : il doit **renommer et requalifier** l'organisation personnelle (`PATCH` name, `kind:'company'`), pas en créer une seconde. À reporter dans la spec P2.5.
- **Valeurs par défaut** d'une nouvelle organisation : pays et devise = pays de l'utilisateur, sinon CM/XAF ; locale = celle de l'utilisateur ; région `eu-fr` (comme P2.1).

### 3.4 Invitations (D-c)

- **Création**, permission `members.invite`, Idempotency-Key :
  - l'invitant doit avoir le statut `active` (Q18) ;
  - rôle invitable : `admin | developer | operator | viewer` (jamais `owner` : un Owner s'obtient par le transfert, ou par l'admin en P2.6) ;
  - un Admin ne peut pas inviter un `admin` ? **Si, il le peut** : la permission couvre les rôles qui ne sont pas Owner ;
  - verrou `FOR UPDATE` sur l'organisation ;
  - limite `workspace.members.max` : membres actifs + invitations en attente non expirées < max, sinon `BILLING_PLAN_LIMIT_REACHED` `{limit:'workspace.members.max', max, used}` ;
  - e-mail déjà membre → 409 `PLATFORM_CONFLICT` `{reason:'already_member'}`. Seule l'organisation l'apprend, et elle voit déjà ses membres ;
  - invitation en attente non expirée → 409 `{reason:'invitation_pending'}` (le front propose « Renvoyer ») ; invitation expirée → révoquée puis recréée ;
  - jeton de 32 octets aléatoires en base64url, stocké `sha256` (le `hashToken` de P2.1 convient à un jeton à forte entropie), `expires_at = now() + 7 jours` calculé par la base ;
  - la réponse ne dit jamais si l'e-mail a un compte sur la plateforme.
- **Renvoi** : rotation de `token_hash` + `expires_at` sur la même ligne (le `public_id` reste stable) ; 3 renvois par 24 h. **Révocation** : `revoked_at`.
- **Aperçu public** (`preview`) : organisation (nom), invitant (nom), e-mail, rôle, `expires_at`. Jeton inconnu, accepté ou révoqué → 422 `AUTH_VERIFICATION_TOKEN_INVALID` ; expiré → 422 `AUTH_VERIFICATION_TOKEN_EXPIRED`.
- **Acceptation avec session** (`POST /v1/invitations/accept`) :
  - transaction `withOrgContext({orgId: invitation.org, userId})`, `FOR UPDATE` sur l'invitation et sur l'organisation, contrôles revus sous verrou ;
  - `lower(user.email) = invitation.email` ; sinon, si `user.email IS NULL`, l'adresse est rattachée et marquée vérifiée si elle est libre (Q8) ; sinon 403 `AUTH_INVITATION_EMAIL_MISMATCH` ;
  - un compte `pending` dont l'e-mail correspond passe `active` avec `email_verified_at = now()`, car le jeton prouve la boîte ;
  - limite des membres revérifiée (une rétrogradation a pu intervenir) ;
  - déjà membre → 200 idempotent, invitation marquée acceptée, rôle inchangé ;
  - effets : `accepted_at`, appartenance `(role, invited_by_user_id)`, `default_org_id` mis à jour si l'utilisateur n'en a pas, audit.
- **Acceptation avec inscription** (`POST /v1/invitations/accept-signup`) :
  - `assertSignupAllowed({via:'invitation'})` ;
  - l'e-mail vient de l'invitation et n'est pas modifiable ;
  - e-mail déjà associé à un compte → 409 `AUTH_EMAIL_ALREADY_EXISTS`. Le porteur du jeton (le propriétaire de la boîte) apprend donc que le compte existe : risque accepté et documenté, comme R3 de P2.2 ;
  - création de l'utilisateur (`status active`, `email_verified_at now()`, argon2id, politique de mot de passe de P2.1), **sans organisation personnelle**, appartenance, session, cookie ;
  - le tout en une transaction ; un échec annule tout et l'invitation reste en attente.
- **Une nouvelle invitation ne retire aucun droit existant.** Le retrait d'un membre ne révoque pas ses sessions (elles sont au niveau de l'utilisateur) : son accès à l'organisation tombe à la requête suivante (404).

### 3.5 Rôles, au moins un Owner, transfert (D-d)

- **Changement de rôle** (`members.manage`) :
  - seul un Owner peut attribuer ou retirer le rôle `owner` et modifier ou retirer un membre Owner ;
  - un Admin gère `admin`, `developer`, `operator` et `viewer` ;
  - modifier son propre rôle est interdit, sauf pour un Owner quand un autre Owner actif existe (le trigger protège de toute façon).
- **Retrait** (`members.manage`) ou **départ** (soi-même, tout rôle) : refusé pour le dernier Owner → 409 `AUTH_LAST_OWNER_REQUIRED`.
- **Transfert** (`POST …/ownership-transfer`, Owner seulement) :
  - corps : `new_owner_membership_id`, `confirmation` (nom exact de l'organisation), `previous_owner_role` (défaut `admin`) ;
  - la cible doit être une appartenance active de **cette** organisation, sinon 404 ;
  - se désigner soi-même → 422 ;
  - confirmation incorrecte → 422 `PLATFORM_VALIDATION_ERROR` `{field:'confirmation'}` ;
  - une transaction : `FOR UPDATE` sur l'organisation, la cible passe `owner`, l'auteur passe `previous_owner_role`, audit `organization.ownership_transferred`, e-mails aux deux personnes après le commit ;
  - la cible n'a pas à accepter (Q9).
- **Concurrence** : le verrou sur l'organisation sérialise tout. Le second transfert relit l'appartenance après l'attente : son auteur n'est plus Owner → 403 `AUTH_INSUFFICIENT_PERMISSIONS`.
- **Trigger différé** (§4) : défense en profondeur contre un oubli de verrou dans un futur service.
- **Hors périmètre** : approbation au sens de l'invariant 6 (réservée aux actions d'un modèle) ; ré-authentification (P8.8).

### 3.6 Workspaces et environnements (D-e)

- **Workspace** :
  - création (`workspaces.create`) sous la limite `workspace.workspaces.max` (workspaces non supprimés et non archivés) ;
  - elle crée `production` + `sandbox` (comme 0003) ;
  - slug dérivé du nom (translittération, 2 à 63 caractères), suffixe `-2`, `-3`… en cas de collision, 409 si l'appelant fournit un slug déjà pris ;
  - modification (`workspaces.manage`) : nom, description, avec `lock_version` → 409 `PLATFORM_CONFLICT` en cas de conflit ;
  - archivage (`workspaces.manage`) : interdit pour le dernier workspace actif (409 `{reason:'last_workspace'}`).
- **Environnement** :
  - création (`workspaces.manage`) de `development` ou `staging` seulement (`production` existe déjà ; `custom` = Enterprise, exclu) ;
  - limite `workspace.environments.max` par workspace, **sandbox exclue** (Q2) ;
  - suppression douce (`deleted_at`) ; `production` et `sandbox` ne se suppriment pas (409) ;
  - renommage autorisé.
- **Bandeau « Mode test »** sur la page Mode test seulement : il n'y a pas encore de sélection d'environnement (C14).
- **Portefeuilles** : 3 portefeuilles de l'organisation (llm, infra, test), solde 0, créés avec l'organisation (Q13). Le portefeuille test n'est jamais débité par la production (P3.1).

### 3.7 Lecteur minimal des limites de plan (préfigure P3.2)

- `orgs.entitlements.ts`, fonction `getLimit(tx, featureKey)` :
  - plan = souscription vivante (le variant BYOK a les droits de son plan de base, déjà copiés par le seed), sinon `free` ;
  - valeur = surcharge non expirée de `organization_feature_overrides`, sinon `plan_features` ; `-1` = illimité.
- **Ordre des contrôles** : drapeau (aucun drapeau ne concerne ces routes : étape N/A, dite explicitement) → droit du plan → surcharge (incluse dans la valeur) → budget et crédits (N/A, aucune route ne débite).
- **P3.2 remplacera ce module** par la chaîne complète `featureGate`.

### 5.6 Idempotence (middleware `idempotent()`, nouveau, `apps/api/src/middlewares/idempotency.ts`)

- Stockage : `dev.idempotency_keys` sous `withOrgContext`.

- Requête en cours → `locked_until` → 409 `PLATFORM_CONFLICT` `{reason:'idempotency_in_progress'}`.
- 24 h. La purge des clés expirées est un job P3 (noté).
- `POST /v1/organizations` est traité par la fonction SQL (§4.1, 5c).

## 11. Points d'attention

- **Sécurité** :
  - 404 pour tout ce qui appartient à une autre organisation.
  - Le jeton d'invitation n'apparaît jamais dans les logs : ajouter `token` au `redact` (déjà présent), éviter le jeton dans l'URL de l'API (corps POST seulement). L'URL du web contient le jeton comme `reset-password` : `Referrer-Policy: no-referrer` sur `/invitations/accept`.
  - CSRF sur tous les nouveaux modules.
  - `requireAuth` accepte aussi le Bearer : conserver le CSRF.
  - Les grants revus (`role_permissions`, surcharges) sont un correctif de sécurité à signaler dans la PR.
- **Pools** : `app_auth` sert seulement à résoudre (appartenance, jeton). Toutes les écritures passent par `app_rw` + contexte. Jamais `app_admin` dans l'API (les fixtures de tests seulement, via `@cp/db/admin`).
- **Coûts et crédits** : aucune route ne débite. Portefeuilles à 0 créés seulement. P3.1 : ne pas recréer les portefeuilles, utiliser ceux-ci.
- **Performance** :
  - `orgContext` = 1 à 2 requêtes `app_auth` par requête : acceptable, cache court par session à étudier en P8.4 ;
  - le cache des permissions évite le N+1 ;
  - listes jointes en une requête (`memberships JOIN users`).
- **Cas limites** :
  - utilisateur `pending` qui accepte → activé ;
  - membre retiré dont l'organisation est `default_org_id` → la préférence est remise à NULL dans la même transaction ;
  - retrait du dernier Owner par cascade lors de la suppression d'un utilisateur (R5, anonymisation) : bloqué par le trigger, comportement voulu, à traiter dans le lot anonymisation ;
  - la rétrogradation de plan en P3.4 doit révoquer les invitations au-delà de la limite (note pour P3.4).
- **Hors périmètre, marqué** :
  - suppression d'organisation (Q15) ;
  - équipes, rôles personnalisés et `workspace_members` (P9) ;
  - projets ;
  - sélecteur d'environnement (P6) ;
  - collecte de la liste d'attente (Q6) ;
  - audit des refus (P2.6) ;
  - feature flags (aucun ne concerne ces routes) ;
  - Marketplace et garde-fous IA (aucun modèle n'agit dans ce lot) ;
  - persistance de `technical_mode` dans `user_preferences` (possible avec S4, mais non demandée : à ajouter si Dylan le souhaite).
- **Décisions à ajouter dans 06 après validation** : D-a à D-i (§0).
